# 如何为 AI Agent 写好一个 Skill（Cursor）

Skill 是教 Agent **在特定场景下怎么做事** 的 Markdown 说明：按团队规范做 Code Review、按固定格式写提交信息、查你们库里的表结构、走一遍你们内部的发布流程——凡是「通用模型不知道、但你希望它每次都照做」的内容，都适合放进 Skill。

下面按「先想清楚 → 再写文件 → 最后自检」的顺序整理，并对应 Cursor 里 `SKILL.md` 的常见写法。

---

## 动笔前先想清楚六件事

1. **目的与边界**：这个 Skill 只解决哪一类任务？不包什么？
2. **放哪**：个人全局 `~/.cursor/skills/`，还是项目内 `.cursor/skills/`（跟仓库走）？
3. **触发场景**：用户说什么、或打开什么文件时，Agent 应该**优先**加载这份说明？
4. **领域知识**：哪些是模型**默认不知道**、必须写下来的（内网地址、命名规范、禁止操作）？
5. **输出形态**：要不要固定模板（报告结构、Commit 格式、回复分段方式）？
6. **已有范例**：仓库里有没有现成文档或历史 PR 可以当作「金标准」？

有对话上下文时，也可以从你们已经反复纠正过的流程里「抽」出一个 Skill，避免每次重讲一遍。

---

## 目录与文件结构

Skill 是一个**目录**，里面至少要有 `SKILL.md`：

```text
skill-name/
├── SKILL.md          # 必填：主说明
├── reference.md      # 可选：细则、API 说明
├── examples.md       # 可选：正反例
└── scripts/          # 可选：可执行脚本
    └── validate.py
```

**存放位置**

| 类型 | 路径 | 作用域 |
|------|------|--------|
| 个人 | `~/.cursor/skills/skill-name/` | 所有项目可用 |
| 项目 | `.cursor/skills/skill-name/` | 跟仓库共享给协作者 |

**注意**：不要往 `~/.cursor/skills-cursor/` 里写自定义 Skill，那是 Cursor 内置技能目录，由系统维护。

---

## `SKILL.md` 必备形态：YAML 头 + 正文

```markdown
---
name: your-skill-name
description: 一句话说明「做什么」+「什么时候用」，并带上触发词
---

# 技能标题

## 指令
分步、可执行的说明。

## 示例
具体输入输出或操作示例。
```

**元数据字段**

| 字段 | 要求 | 作用 |
|------|------|------|
| `name` | 最多 64 字符，小写、数字、连字符 | 标识符 |
| `description` | 非空，最多 1024 字符 | **Discovery 核心**：Agent 靠它判断要不要用这份 Skill |

---

## 写好 `description`：决定「会不会被用上」

描述会进系统提示，建议：

1. **第三人称**，不要写「我帮你…」「你可以…」。
2. **具体 + 触发词**：写明能力边界和用户可能用的词（PDF、PR、commit、某业务名）。
3. **同时写 WHAT 与 WHEN**：做什么 + 什么情况下启用。

**示例（意译自官方）**

- PDF：`从 PDF 抽取文本与表格、填表、合并文档。处理 PDF、表单、文档抽取时使用。`
- Excel：`分析表格、透视、出图。分析 .xlsx、表格数据时使用。`
- Git：`根据 diff 写说明性提交信息。用户要写 commit 或看暂存变更时使用。`

---

## 正文写作原则

### 1. 能短则短

上下文要分给对话、其它 Skill 和当前请求。默认假设模型已经很强：**只写它没有就做不到的事**。写完自问：这段是否值得占 token？

### 2. 主文件控制在约 500 行内

细则挪到 `reference.md` / `examples.md`，需要时再让 Agent 读——**渐进式披露**。

### 3. 引用别套娃

从 `SKILL.md` **一层**链到参考文件即可，避免深层嵌套导致读不全。

### 4. 自由度要和任务「脆度」匹配

| 自由度 | 适用 | 例子 |
|--------|------|------|
| 高 | 多种做法都合理 | Code review 原则 |
| 中 | 有偏好模板、可小改 | 报告结构 |
| 低 | 必须一致、易出错 | 迁移脚本、固定命令 |

---

## 常用写法模式

- **模板模式**：直接给出输出 Markdown/JSON 骨架，让 Agent 填槽。
- **示例模式**：Commit、回复、报告各给 1～2 组「输入 → 输出」。
- **流程模式**：步骤 + 勾选清单，复杂任务拆成可跟踪阶段。
- **分支流程**：先判断类型（新建 vs 修改），再指向不同小节。
- **校验闭环**：改完 → 跑 `scripts/validate.py` → 不过就修 → 过了再继续。

### 可选：`scripts/` 里的脚本

比每次现场生成代码更稳、更省 token；正文里写清楚是**让 Agent 执行**还是**仅作参考阅读**。路径在文档里用正斜杠，例如 `scripts/helper.py`。

---

## 反模式（尽量别踩）

1. **路径**：文档里写 `scripts/foo.py`，避免 Windows 反斜杠风格混在说明里造成歧义。
2. **一堆库任选**：先给**默认**方案，例外情况再写「若…则换用…」。
3. **强时效句子**：少写「某月之前用旧接口」；若必须保留，单独放「已废弃」小节。
4. **术语混用**：同一概念固定一个词（例如统一叫「接口」或「端点」）。
5. **Skill 名太泛**：避免 `helper`、`utils`；用 `processing-pdfs` 这类可联想的名字。

---

## 从 0 到 1 的流程（可照抄）

1. **发现**：目的、存放位置、触发语、约束、有无范例。
2. **设计**：`name`、`description`、正文大纲、要不要 reference/scripts。
3. **实现**：建目录 → 写 `SKILL.md` → 按需加附属文件。
4. **验收**：描述是否含触发词；术语是否统一；引用是否一层；主文件是否过长；在实际对话里是否会被正确选用。

## 迷你完整示例（Code Review）

**目录**：`code-review/SKILL.md`（另可有 `STANDARDS.md`、`examples.md`）

```markdown
---
name: code-review
description: 按团队标准审查代码质量、安全与可维护性。在审 PR、看 diff、或用户明确要求 code review 时使用。
---

# Code Review

## 快速流程

1. 正确性与边界情况  
2. 安全实践  
3. 可读性与可维护性  
4. 测试是否覆盖变更  

## 反馈格式

- 🔴 **必须改**：合并前必须处理  
- 🟡 **建议**：值得考虑  
- 🟢 **加分项**：可选优化  

## 更多

- 细则见 [STANDARDS.md](STANDARDS.md)  
- 范例见 [examples.md](examples.md)  
```

---

## 定稿前自检清单

**质量**

- [ ] `description` 具体，含关键词，且为第三人称  
- [ ] 同时交代「做什么」和「何时用」  
- [ ] 正文精简，主文件不过长  
- [ ] 术语一致，示例具体  

**结构**

- [ ] 外链/附件一层可达  
- [ ] 复杂内容已拆到 reference，主文件只保留「足够启动」的部分  
- [ ] 无难维护的强时效表述  

**若含脚本**

- [ ] 用途明确（执行 vs 只读）  
- [ ] 依赖与用法可复现  

---

以上内容对齐 Cursor Agent Skills 的常见约定：用 **`description` 做发现**，用 **`SKILL.md` 正文做执行契约**，用 **附属文件与脚本做渐进披露**。你若有具体业务（例如「只在我们内网 API 上这样调」），把**模型不知道的那部分**写进 Skill，比写一百行通用编程课更有用。
